## きっかけ

TODO-106（`docs/User.md`）と TODO-107（`docs/Architecture.md`）で
文書を整えたあと、README だけが手つかずで残っていた。冒頭に
「【未完成】」とだけ書いてあり、末尾の「A. 手回しオルガン用ロール・ブック」
はメモを書き捨てたままだった。TODO-106 の作業中に、CLI の `play` を
「試聴する」と書いているのも見つかっていた。

## 決めたこと

「【未完成】」の扱いだけ、着手時に利用者へ確認した。

- **状態を書いた一文に直す。** 削除も、そのまま残すのも採らない。
  未完成であることは残しつつ、何が未確定なのか（画面と設定ファイルの
  形式）が読み手に伝わるようにする

## やったこと

- **冒頭の「【未完成】」を「**開発中です。** 一通り動きますが、画面や
  設定ファイルの形式は変わることがあります。」に差し替えた**
- **「試聴」を CLI から外した。** 1 章の「音の一覧表示や試聴ができる」と、
  3 章のコマンド例のコメント `# 試聴する` を「再生」に直した。
  `CLAUDE.md`「画面に出す用語」で「試聴」は**ブラウザで鳴らして確かめる
  こと**を指す（TODO-063）
- **末尾の A 節を「5. 同梱の機種設定」に書き直した。** メモの箇条書きを、
  同梱テンプレートの `34notes` の話だと分かる形にした
  - `1秒 = 約5cm` → 「送りの速さは1秒あたり50mm（設定項目
    `mm_per_sec` の既定値）」
  - `34音、低音部で、一部半音がない` / `D#がない` →
    「34音。低音部ほど半音が抜けていて、`D#` はどの高さにも無い」
  - 音の並びも速さも設定項目なので、機種が違えば「機種設定」から
    変えられることを添えた
- **節番号を通した。** `1, 2, 3, A, B` と混ざっていたのを `1`〜`6` に
  揃え、「B. Reference」は「6. 参考」にした
- **ドキュメントの表を独立した節にした。** 3 章「使い方」の子節
  （`### ドキュメント`）だったものを「4. ドキュメント」に上げた。
  リンク先は TODO-106 で足したものをそのまま使っている

## テスト

コードは変えていないので `pytest` / `ruff` / `mypy` の対象は無い。
README に書いたことが実際に成り立つかを verifier に確かめさせた。

- `--help` で、`rollbook` / `parse` / `play` / `webapp` の各サブコマンドと
  オプション（`-m` `-v` `-p`）が実在することを確認
- `rollbook tests/data/sample.mid -m 34notes` を実際に動かして SVG が
  できることを確認（出力はリポジトリの外へ）
- 設定ファイルの探索順が `conf.py` の `SEARCH_PATH` と一致
- `docs/` の 4 文書がすべて実在
- `34notes` の音数（34）、`D#` が無いこと、`mm_per_sec` が 50.0 で
  あることを `conf/storgan-conf.json` と突き合わせ
- `~/Desktop` に書く記述が `apps.py` の `DEF_OUT_DIR` と一致

指摘は 1 件。「同梱のテンプレートには、このほかに20音の設定も
入っている」と書いたが、実際は `34notes` / `20notes` / `20notes a` /
`34notes-a` の 4 つある。**「34音と20音の設定が計4つ入っている」に
直した。** 派生（`20notes a` など）の名前を README に並べるのは細かすぎる
ので、数だけ書いている。

## 分担の振り返り

- **verifier が見つけたのは 1 件**（同梱テンプレートが 4 つある）。
  コマンド、探索順、リンク先、`34notes` の諸元はすべて記述どおりだった。
  main が書いた時点で `conf/storgan-conf.json` の先頭 2 モデルしか
  見ていなかったのが原因で、これは書いた本人には気付きにくい
- **見込みとの食い違いは main のモデルだけ**（Sonnet 5 の見込みが
  Opus 5 になった）。担当は見込みどおり verifier 1 人で足りた
- **次に同じ規模の項目をやるなら、同じ組み方でよい。** 文書だけの項目でも、
  README のように設定ファイルやコマンドと突き合わせる中身があるなら
  verifier は省かない。モデルは Haiku のままでよく、上げる必要は無かった
  （突き合わせる対象がはっきりしていて、判断が要らない）。
  main の負担が 94% を占めたのは、README を書くこと自体が main の
  仕事だったため。実装の担当を分けるほどの分量ではない
